# Chapter 1 — How the project was made

This chapter tells the story in the order the work was actually done. If you want to design your own robot, copy the **order**, not just the result: each step produces the numbers the next step needs.

## 1.1 Start from the wish list, turn it into numbers

The request had 12 features (balance on rough and sloped ground, removable electronics, cute and printable, cameras, fast, jumping, tilting/crawling, payload, autonomy without lidar, halting, GPS missions, phone control). A wish like "run fast" can't be designed for; a number can. So the first job was to give every wish a target:

| Wish | Target I used |
|---|---|
| balance on inclined terrain | climb and stand on ≥ 20° ramps, ≥ 12° side slopes |
| rough terrain | ≥ 5 cm bumps at speed |
| run fast without damage | ≥ 2 m/s with torque to spare, survive falls |
| jump steps / obstacles | ≥ 15 cm steps (a normal curb/stair is 15–18 cm) |
| payload | 2 kg |
| tilt / crawl | ≥ ±15° pitch and roll, noticeably lower stance |

These targets became the **pass/fail tests** of the simulation (chapter 5). Writing the tests from the wish list *before* the design is the single most useful habit in this project.

## 1.2 Choose the architecture (the big decision)

Candidates:

1. **Two‑wheeled self‑balancer (Segway style)** — simple, fast, but it cannot jump, cannot crawl lower, and bumps go straight into the body.
2. **Quadruped (four legs)** — handles stairs, but is slow, heavy, needs 12 motors and very hard control.
3. **Wheel‑legged biped** (Boston Dynamics *Handle*, ETH *Ascento*, Direct Drive *Diablo*) — two legs that end in wheels. Wheels give speed and efficiency; legs give suspension, height change, tilt and jumping.

Option 3 covers the most wishes with the fewest motors (6), so BOLT is a wheel‑legged biped.

Next: what kind of leg? Each leg needs **two** controllable things: its length (for height, crawling, jumping, absorbing bumps) and its angle (to keep the wheel under the body on slopes and while accelerating). The common designs:

* a serial leg (hip motor + knee motor on the leg) — the knee motor rides on the leg, making it heavy and slow to swing;
* a **5‑bar parallel linkage** — both motors sit on the body, the leg is just light printed links. Light legs = fast legs = good jumping. This is what BOLT uses (chapter 3).

## 1.3 Pick motors with a back‑of‑the‑envelope calculation

Guess the mass first (motors + battery + electronics + ~2.5 kg of prints ≈ 6–6.5 kg), then check that motors exist that can:

* **Hold the body**: each leg carries about half the body (~21 N). Through the 5‑bar (chapter 3) that needs ~1.8 Nm per hip motor — fine for a motor rated 3 Nm continuous.
* **Jump**: to lift the body 10–15 cm the legs must push several times the weight for a fraction of a second → several Nm peak, **and** turn fast (≈ 10–20 rad/s). That points to "quasi‑direct‑drive" actuators (a strong brushless motor with a small 6–10:1 gearbox) used in small legged robots. The **DM‑J4310‑2EC** (7 Nm peak, ~20 rad/s, CAN bus, 300 g) is a common, affordable choice.
* **Drive and balance**: a hub motor with ~2–4 Nm and a few hundred rpm on a ~15 cm wheel gives 2–2.5 m/s. The **LK MF9025** direct‑drive hub motor fits.

Then the brains: balancing needs a fast, predictable loop (1000 times per second) → a microcontroller (**Teensy 4.1**, 600 MHz, three CAN buses). Vision, maps, Wi‑Fi and the app need a small computer → **Raspberry Pi 5**. Splitting "fast and simple" from "slow and smart" is standard in robotics: if the Pi crashes, the robot still balances.

## 1.4 Write all dimensions in ONE file

`design/params.py` holds every important number: link lengths, wheel size, body size, where each heavy component sits, motor data. **Everything else reads this file** — the CAD, the simulator, the controller design. Change a number once and the whole chain updates. Three versions of the design (V1, V2, V3) live in the same file so the comparison is reproducible.

## 1.5 Kinematics before CAD

Before drawing a single part, `design/kinematics.py` checks that the leg geometry can reach every required length (0.13 m crouched to 0.35 m stretched) without the links locking up. That's 60 lines of trigonometry (chapter 3) and it decides the link lengths: thigh 140 mm, shin 250 mm, hips 90 mm apart.

## 1.6 CAD as code

The parts are generated by a Python script (`cad/build_parts.py`) using constructive solid geometry: boxes, cylinders and spheres are added and subtracted (chapter 4). Advantages for a beginner: the parts can never disagree with `params.py`, and the script also **weighs every part and finds the centre of mass**, which the simulator needs.

## 1.7 Simulate before building

`sim/robot_model.py` turns params + CAD masses into a MuJoCo physics model: body, the two closed 5‑bar legs, wheels with tyre–ground contact. Then:

1. **Design the controller from the model** (`sim/lqr_design.py`): measure the masses/inertias of the model, build the simplified "wheel + leg + body" equations, compute optimal gains with LQR for 14 different leg lengths (chapter 2).
2. **Write the controller once in C++** (`firmware/lib/bolt_core`). The simulator loads that same C++ file, so what is tested is what will be flashed.
3. **Run the tests** (`sim/test_suite.py`): balance, push, speed, slopes, bumps, payload, tilt, crawl, jump, steps, stairs, hop, recovery.
4. **Read failures, fix, repeat.** Most of the work was here: the first jump attempt fell over, the second detected landing in mid‑air, the third spun the body, and so on. Chapter 5 lists every bug and its fix.
5. **Change the design** where the controller can't fix it: V1 → V2 → V3 (chapter 5).

## 1.8 Then the rest of the system

With a body that balances and jumps in simulation, the remaining layers were added and each was tested against the simulated robot:

* the **brain** on the Pi (`companion/`): line following from the camera image, obstacle map from the sonars, shortest‑path planning (A*), Mission Planner link (MAVLink), behaviours (jump, step‑up, dodge…);
* the **phone app** (`app/`): a web page the robot serves, tested in a headless browser;
* the **firmware** around the controller: motor drivers, IMU, sensors, safety (`firmware/src`);
* the **electronics**: power path, buses, pins (`electronics/`, chapter 6).

## 1.9 Be honest about results

Every number in the docs comes from a test that can be re‑run. When a test failed and couldn't be fixed (multi‑step stairs, getting up after a fall), it is written down as a limit with a reason and a fix path. One test was even made *stricter* after it gave a flattering number (push recovery — chapter 5).

## 1.10 Tools used (all free)

| Tool | Used for |
|---|---|
| Python 3, NumPy, SciPy | design maths, LQR (`scipy.linalg.solve_continuous_are`) |
| manifold3d + trimesh | CAD solids, STL export, mass properties |
| MuJoCo | physics simulation and rendering |
| matplotlib | plots and diagrams |
| g++ / arm‑none‑eabi‑g++ | compiling the controller for the PC (sim) and for the Teensy |
| PlatformIO / Teensyduino | building and flashing the Teensy firmware |
| OpenCV | camera image processing |
| pymavlink | talking to Mission Planner |
| aiohttp | the robot's web server for the app |
| Playwright (Chromium) | testing the app automatically |

## 1.11 If you want to reproduce it

```bash
python3 cad/build_parts.py        # parts + masses
python3 sim/lqr_design.py         # controller gains (also writes the firmware header)
python3 sim/test_suite.py V3      # the 15 tests
python3 sim/companion_sim.py --demo all
python3 sim/make_report.py        # the report figures
```
Change something in `design/params.py` and run the same commands to see what your change does.
